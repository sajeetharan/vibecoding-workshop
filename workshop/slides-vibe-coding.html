The Three Core Cursor Moves

1️⃣ Chat (Ctrl+K / Cmd+K)

Ask questions about code, request refactors, debug issues. Chat sees your entire codebase context.

2️⃣ Tab Completion (Tab)

Start typing. Cursor predicts next line or function. Press Tab to accept, Esc to reject.

3️⃣ Edit (Ctrl+L / Cmd+L)

Select code, press Ctrl+L, describe what to change. Cursor edits inline with a diff preview.

Speaker Notes

  • Chat (Ctrl+K): For strategic questions. "Why is this component re-rendering?" "How do I handle auth?"
  • Tab Completion: Tactical, fast. You type, Cursor suggests the next lines. Press Tab to accept or Esc to reject.
  • Edit (Ctrl+L): Best for refactoring. Highlight messy code, ask Cursor to "improve this" or "split into helpers".
  • Live demo moment: Show all three on a simple file. 2 minutes of demo saves 10 minutes of confusion.
  • Remember: These three moves unlock 80% of Cursor's daily power. Master them and you're unstoppable.

Tab Completion: Real-Time Coding Partner

How it works: Start typing code. After a few characters, a gray suggestion appears. Press Tab to accept or Esc to dismiss.

✅

Best for:

Repeating patterns, boilerplate, function signatures you've used before

⚠️

Be cautious with:

Security-critical code, business logic, edge cases. Always review before accepting.

Speaker Notes

  • Tab Completion demo: Start a function, type "function get", wait 1 second, gray suggestion appears.
  • When to use: Boilerplate (loops, array methods), repeat patterns you've already typed.
  • When NOT to use: Security code (auth, crypto), domain logic (business rules), complex algorithms.
  • Rule of thumb: If you understand what the code does in 2 seconds, accept it. Else, reject and chat instead.
  • Speed benefit: Experienced developers see 30-40% faster typing with tab completion.

Codebase Context: Your Secret Weapon

Cursor reads your files to give smarter answers.

What Cursor Can See

  • Open files and tabs
  • File structure and dependencies
  • Your project's naming patterns and conventions
  • Package.json, tsconfig, .env (not secrets)

💡 Pro tip: Keep related files open in tabs. Cursor uses them for better context. Close unrelated tabs to avoid noise.

Speaker Notes

  • Context is power: Cursor reads your current files to avoid hallucinating wrong API names or patterns.
  • What Cursor sees: All open tabs, file structure, imports, even comments that explain your architecture.
  • What Cursor can't see: Secret keys, production databases, your mind.
  • Best practice: Open only files related to your task. If building auth, keep auth files open. Close unrelated projects.
  • Real-world impact: Good context = Cursor suggests code that actually fits your codebase. Bad context = suggestions you can't use.

Ground Rules for AI-Assisted Building

  • Small steps over big rewrites
  • Read before accepting generated code
  • Validate behavior after each change
  • Track assumptions explicitly
  • Keep a human decision log

Speaker Notes

  • Key principle: AI is a tool, not a replacement for engineering judgment.
  • Small steps: Don't ask for "build entire app". Ask for "build login endpoint", then next piece.

Prompt Pattern 1: Scope First

📋 Prompt: "Propose a 60-minute implementation plan. Keep scope small, list files to change, add acceptance criteria."

❌

Vague: "Build a full app with all features and make it scalable."

✅

Sharp: "Build POST /api/generate-cv only. Accept GitHub URL and Stack Overflow URL, validate both, return structured CV JSON. Time box: 20 mins."

Speaker Notes

  • Scoping mindset: Start small. Deliver one piece, then build up.
  • Why vague fails: "Make it scalable" means different things. AI guesses and you get 50MB of code.
  • Why sharp wins: AI knows exactly what to build, when it's done, and how to validate.
  • Time boxing is power: "20 mins" tells AI: stop at MVP, don't gold-plate.
  • Use this pattern: Every single prompt you write today, scope it first.

Prompt Pattern 2: Focused Build

🎯 Prompt: "Implement feature X with the smallest maintainable change. Do not touch unrelated files."

🔨

Surgical approach: One file, one feature, minimal blast radius

👀

Easier to review: Your teammate can understand the change in 30 seconds

🐛

Fast debugging: Broke something? Revert one diff, not 10

Speaker Notes

  • Surgical principle: One feature, one file, minimal change = low risk of side effects.
  • Why it matters: If review takes 30 seconds instead of 5 minutes, you unblock teammates faster.
  • Debugging benefit: If something breaks, you know exactly which change caused it. One revert fixes it.
  • Prompt phrase: Always include "Do not touch unrelated files" or "Keep changes minimal".
  • Real-world impact: Big rewrites fail code review. Small, focused PRs ship. Train your prompts accordingly.

Prompt Pattern 3: Review and Risk

🔍 Prompt: "Review this diff as a senior engineer. List bugs, edge cases, and regressions by severity."

Critical (🔴): Null pointer, SQL injection, infinite loop

Major (🟠): Memory leak, broken API contract, performance cliff

Minor (🟡): Typo, inconsistent naming, missing comment

Speaker Notes

  • Review mindset: AI often generates working code but not SAFE code. This pattern fixes that.
  • Ask AI to play security auditor: "Review as a senior engineer" triggers better analysis.
  • Severity framework: Critical (production down), Major (silent failures), Minor (nice-to-fix).
  • Follow-up prompt: "Fix the critical and major issues. Explain each one."
  • Team practice: Have teams code-review each other's AI output using this pattern.

Prompt Pattern 4: Debug Fast

🔧 Prompt: "Given this error and current code, list 3 likely root causes and lowest-risk fix first."

1️⃣

Reproduce

Exact steps to break it

2️⃣

Hypothesize

3 possible root causes

3️⃣

Patch

Try lowest-risk fix first

4️⃣

Verify

Reproduce same steps again

Speaker Notes

  • Debugging methodology: Follow this systematic approach when code breaks.
  • 1. Trace: Don't guess. Add logs, use browser DevTools, understand the flow.
  • 2. Hypothesize: Make 3 guesses. "Could be authentication", "Could be CORS", "Could be schema mismatch".
  • 3. Patch: Try the safest fix first. Don't refactor while debugging.
  • 4. Verify: Run exact same steps again. Confirm fix is real, not coincidence.
